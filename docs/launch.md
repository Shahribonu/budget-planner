# Launch

Phase 4 of the product plan: hosting, security review, load test, privacy, and the
launch checklist.

## Hosting

Uzbekistan's personal data law requires personal data of Uzbek citizens to be stored on
servers located in Uzbekistan. Pick a provider with a data center in Uzbekistan, and
confirm with a local lawyer whether the operator must be registered in the state
register of personal data databases.

One small VPS is enough for the beta and well beyond it (see the load test below):

- 2 vCPU, 2–4 GB RAM, 40 GB SSD, Ubuntu 24.04
- a public IPv4 address and a domain (or subdomain) pointing at it
- outbound HTTPS to api.telegram.org (and api.anthropic.com if the AI fallback is on)

### First deploy

```sh
# on the server
sudo apt install -y docker.io docker-compose-v2 git
git clone https://github.com/Shahribonu/budget-planner.git && cd budget-planner/deploy
cp .env.example .env && chmod 600 .env && nano .env   # DOMAIN, passwords, bot token, webhook secret
docker compose up -d --build
docker compose logs -f app                             # wait for "listening"
```

Caddy gets a TLS certificate for `DOMAIN` automatically. The app runs migrations,
registers the webhook at `https://DOMAIN/telegram/webhook` and serves the Mini App at
`https://DOMAIN/`.

In @BotFather, set the Mini App URL (Bot Settings → Configure Mini App) to
`https://DOMAIN/`, so the menu button opens the right place.

### Updates

```sh
cd budget-planner && git pull && cd deploy && docker compose up -d --build app
```

### Backups

The `backup` service writes `deploy/backups/budget_planner-YYYY-MM-DD.sql.gz` every 24
hours and keeps 14 days. The deletion promise in the privacy policy depends on that
14-day window: don't keep backups longer without changing the policy.

Test a restore before launch, and then monthly:

```sh
docker compose exec db createdb -U budget restore_check
gunzip -c backups/<latest>.sql.gz | docker compose exec -T db psql -q -U budget -d restore_check
docker compose exec db psql -U budget -d restore_check -c "select count(*) from users; select count(*) from transactions;"
docker compose exec db dropdb -U budget restore_check
```

Copy backups off the server too, to a second location that is also in Uzbekistan.

## Security review

| Area | Status |
| --- | --- |
| Mini App auth | initData HMAC checked on every request, 24 h freshness; the user id never comes from the client |
| Dev login | only with `APP_ENV=development`; production images set `APP_ENV=production` |
| Ownership | every query is scoped by `user_id`; covered by API tests |
| SQL | generated by sqlc, parameterized only |
| Webhook | secret token compared in constant time; updates idempotent by `update_id` |
| Rate limits | 10 req/s per user (burst 30); failed logins 1/s per IP (burst 20), and valid users behind the same carrier NAT are never blocked |
| Request size | API bodies capped at 64 KB |
| Logs | method, route, status and timing only, with no amounts, descriptions or tokens; the bot token is stripped from Telegram client errors |
| Headers | `nosniff`, `Referrer-Policy`, HSTS from Caddy; no `X-Frame-Options`, because Telegram Web shows Mini Apps in an iframe |
| Card numbers | only the last 4 digits are kept; long digit runs are masked before any AI call |
| Secrets | `.env` files only, `chmod 600`, never committed |
| Dependencies | `govulncheck` and `npm audit` run in CI; Go is pinned to a patched toolchain |
| Payments | none: Premium is removed; pre-checkout queries from old invoice links are refused |

Open items:

- **Database at rest:** enable disk encryption on the VPS if the provider offers it.
- **Off-site backups:** copy them somewhere else and test restoring from there.
- **Monitoring:** add an uptime check on `https://DOMAIN/healthz` (any external pinger) and alert on failures.

## Load test

`go run ./cmd/loadtest` simulates Mini App users: Home (four parallel calls), logging an
expense, and plan, budgets or history, with random pauses. Run it against a throwaway
server and database only.

Results on a MacBook Air (M-series), server and Postgres on the same machine, 28 Oct 2026:

| Users | Duration | Requests/s | Errors | p95 | p99 |
| --- | --- | --- | --- | --- | --- |
| 300 | 60 s | 324 | 0 | ≤ 9 ms | ≤ 15 ms |
| 1,000 | 90 s | 1,956 | 0 | ≤ 5 ms | ≤ 47 ms |

1,000 users with a ~1 s pause are far more traffic than 1,000 real users produce, since
real people open the app a few times a day. The beta target of 30–50 users is no load
concern. Re-run on the production VPS before the public launch.

## Privacy

- **Policy and terms:** shown in the app at `#/legal/privacy` and `#/legal/terms` (uz-Latn, uz-Cyrl, ru, en). The bot's `/privacy` command links to them. Source: `app/src/legal/content.ts`.
- **Consent:** accepted in onboarding, and existing users are asked once. Changing the meaning of the texts requires raising `TermsVersion` in `backend/internal/api/privacy.go`, which asks everyone again.
- **Export:** Profile → Data and privacy sends CSV and JSON files to the bot chat.
- **Deletion:** Profile → Data and privacy deletes the user and everything they own, immediately.
- **Retention:** resolved drafts (which hold raw message text) are purged after 7 days, and voice audio is never stored.

The texts are a draft and the service is free, with no payments. Legal review is
deferred: do it before a public launch, together with filling in `legalContacts`
(operator name and contact) in `content.ts`.
